### 🌱 포스팅 작성 이유

MSA를 이야기할 때 Kafka 같은 메시지 브로커가 빠지지 않고 등장합니다. 하지만 모놀리스 단계에서 브로커부터 도입할 필요는 없습니다. 먼저 필요한 것은 도구가 아니라, 모듈끼리 **이벤트로 대화하는 구조**입니다.

이벤트 기반 설계가 무엇을 바꾸는지, 지금 단계에서 무엇을 준비해 둘 수 있는지를 Spring Boot 코드로 정리합니다. 프레임워크와 무관한 개념 설명은 [이벤트 기반 아키텍처: 호출 대신 사실을 알린다](/blog/groups/cs/architecture/event_driven_architecture)에 따로 정리했습니다.

---

## 1. 직접 호출 대신 이벤트로 알린다

회원(`member`)이 탈퇴하면 주문(`order`) 쪽에서도 처리할 일이 있다고 하겠습니다. 이 글에서는 이렇게 업무 단위로 나눈 영역을 **BC(Bounded Context)** 라고 부릅니다.

### 1.1 직접 호출하면 생기는 문제

가장 단순한 방법은 회원이 주문을 직접 부르는 것입니다.

<CodeTabs>

```java
// ❌ member 모듈이 order 모듈을 알고 있다
@Service
public class MemberService {
    private final MemberRepository memberRepository;
    private final OrderService orderService;

    public MemberService(MemberRepository memberRepository, OrderService orderService) {
        this.memberRepository = memberRepository;
        this.orderService = orderService;
    }

    @Transactional
    public void withdraw(Long memberId) {
        Member member = memberRepository.getReferenceById(memberId);
        member.withdraw();
        orderService.handleMemberWithdrawn(memberId);
    }
}
```

```kotlin
// ❌ member 모듈이 order 모듈을 알고 있다
@Service
class MemberService(
    private val memberRepository: MemberRepository,
    private val orderService: OrderService,
) {
    @Transactional
    fun withdraw(memberId: Long) {
        val member = memberRepository.getReferenceById(memberId)
        member.withdraw()
        orderService.handleMemberWithdrawn(memberId)
    }
}
```

</CodeTabs>

| 문제 | 내용 |
| --- | --- |
| 회원이 주문을 알게 된다 | 탈퇴는 회원의 일인데, 회원 코드가 주문의 존재와 메서드 이름까지 알아야 한다 |
| 관심 있는 곳이 늘 때마다 회원 코드를 고친다 | 쿠폰, 알림, 리뷰가 탈퇴에 반응해야 하면 `withdraw()`에 호출이 계속 추가된다 |
| 남의 실패가 내 실패가 된다 | 주문 쪽 처리에서 예외가 나면 탈퇴 자체가 실패한다 |

### 1.2 이벤트로 바꾸기

회원은 "회원이 탈퇴했다"는 **사실**만 알리고, 그 소식이 필요한 쪽이 각자 받아서 처리하게 합니다.

```text
Member BC
    │
    │  MemberWithdrawn
    ▼
  이벤트
    │
    ▼
Order BC
    │
    ▼
회원과 관련된 후속 처리
```

Spring에서는 메시지 브로커 없이도 프로세스 안에서 이벤트를 주고받을 수 있습니다.

<CodeTabs>

```java
// 이벤트 : 이미 일어난 사실이므로 과거형으로 이름 짓는다
public record MemberWithdrawn(
        Long memberId,
        Instant withdrawnAt
) {}
```

```kotlin
// 이벤트 : 이미 일어난 사실이므로 과거형으로 이름 짓는다
data class MemberWithdrawn(
    val memberId: Long,
    val withdrawnAt: Instant,
)
```

</CodeTabs>

<CodeTabs>

```java
// member 모듈 : 사실을 알리기만 한다
@Service
public class MemberService {
    private final MemberRepository memberRepository;
    private final ApplicationEventPublisher events;

    public MemberService(MemberRepository memberRepository, ApplicationEventPublisher events) {
        this.memberRepository = memberRepository;
        this.events = events;
    }

    @Transactional
    public void withdraw(Long memberId) {
        Member member = memberRepository.getReferenceById(memberId);
        member.withdraw();
        events.publishEvent(new MemberWithdrawn(memberId, Instant.now()));
    }
}
```

```kotlin
// member 모듈 : 사실을 알리기만 한다
@Service
class MemberService(
    private val memberRepository: MemberRepository,
    private val events: ApplicationEventPublisher,
) {
    @Transactional
    fun withdraw(memberId: Long) {
        val member = memberRepository.getReferenceById(memberId)
        member.withdraw()
        events.publishEvent(MemberWithdrawn(memberId, Instant.now()))
    }
}
```

</CodeTabs>

<CodeTabs>

```java
// order 모듈 : 소식을 듣고 자기 할 일을 한다
@Component
public class MemberWithdrawnHandler {
    private final OrderService orderService;

    public MemberWithdrawnHandler(OrderService orderService) {
        this.orderService = orderService;
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void handle(MemberWithdrawn event) {
        orderService.handleMemberWithdrawn(event.memberId());
    }
}
```

```kotlin
// order 모듈 : 소식을 듣고 자기 할 일을 한다
@Component
class MemberWithdrawnHandler(
    private val orderService: OrderService,
) {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    fun handle(event: MemberWithdrawn) {
        orderService.handleMemberWithdrawn(event.memberId)
    }
}
```

</CodeTabs>

`@TransactionalEventListener`의 `AFTER_COMMIT`은 "탈퇴 트랜잭션이 커밋된 뒤에 실행하라"는 뜻입니다. 탈퇴가 롤백됐는데 후속 처리만 실행되는 일을 막아 줍니다.

| | 직접 호출 | 이벤트 |
| --- | --- | --- |
| 회원이 아는 것 | 주문의 클래스와 메서드 | 자신이 발행하는 이벤트뿐 |
| 반응하는 곳이 늘어나면 | 회원 코드를 고친다 | 리스너만 추가한다 |
| 의존 방향 | 회원 → 주문 | 주문 → 회원의 이벤트 |

회원은 누가 이 이벤트를 듣는지 모릅니다. 듣는 쪽이 하나든 다섯이든 회원의 코드는 그대로입니다.

이 구조를 갖춰 두면, 나중에 서비스를 분리할 때 이벤트가 지나가는 길만 프로세스 내부에서 메시지 브로커로 바꾸면 됩니다.

## 2. Domain Event와 Integration Event

위 예시에서 주문 모듈은 회원 모듈의 `MemberWithdrawn` 클래스를 그대로 받아 씁니다. 모놀리스에서는 동작하지만, 이벤트의 종류를 구분하지 않으면 나중에 곤란해집니다.

| | Domain Event | Integration Event |
| --- | --- | --- |
| 의미 | BC **내부**에서 일어난 비즈니스 사실 | **다른 서비스에 전달**하려고 정의한 계약 |
| 듣는 쪽 | 같은 BC 안의 코드 | 다른 BC, 다른 서비스 |
| 바꾸기 | 자유롭다. 내부 구현의 일부다 | 조심해야 한다. 바꾸면 듣는 쪽이 깨진다 |
| 담는 내용 | 내부 모델을 그대로 써도 된다 | 외부에 공개해도 되는 최소한의 값 |

둘을 구분하지 않고 내부용 이벤트를 그대로 밖으로 내보내면, 회원 BC의 내부 구조를 고칠 때마다 그 이벤트를 듣는 모든 서비스가 영향을 받습니다. 공개 API의 응답 형식을 함부로 바꿀 수 없는 것과 같은 이유입니다.

그래서 필요하면 두 이벤트를 **별도의 모델**로 둡니다.

<CodeTabs>

```java
// Domain Event : member BC 내부용. 내부 타입을 써도 된다
public record MemberWithdrawn(
        Member member,
        WithdrawalReason reason
) {}

// Integration Event : 외부 공개용. 원시 값만 담고, 형식을 쉽게 바꾸지 않는다
public record MemberWithdrawnIntegrationEvent(
        String eventId,
        Long memberId,
        Instant occurredAt
) {}
```

```kotlin
// Domain Event : member BC 내부용. 내부 타입을 써도 된다
data class MemberWithdrawn(
    val member: Member,
    val reason: WithdrawalReason,
)

// Integration Event : 외부 공개용. 원시 값만 담고, 형식을 쉽게 바꾸지 않는다
data class MemberWithdrawnIntegrationEvent(
    val eventId: String,
    val memberId: Long,
    val occurredAt: Instant,
)
```

</CodeTabs>

회원 BC는 내부에서 Domain Event를 발행하고, 외부에 알려야 하는 것만 Integration Event로 변환해 내보냅니다. `eventId`는 받는 쪽이 같은 이벤트를 두 번 받았는지 확인하는 데 씁니다.

모든 이벤트를 처음부터 둘로 나눌 필요는 없습니다. BC 밖으로 나가는 이벤트는 "한번 공개하면 바꾸기 어려운 계약"이라는 점만 의식하고 있으면 됩니다.

## 3. 신뢰할 수 있는 이벤트 전달

이벤트로 연결하면 새로 챙겨야 할 것이 생깁니다. **이벤트가 사라지지 않는다는 보장**입니다.

### 3.1 데이터베이스 커밋과 메시지 발행은 한 몸이 아니다

회원 탈퇴는 "데이터베이스에 탈퇴를 기록하는 일"과 "이벤트를 발행하는 일" 두 가지로 이루어집니다. 이 둘은 서로 다른 시스템을 상대하므로 트랜잭션 하나로 묶이지 않습니다. 어느 순서로 하든 틈이 생깁니다.

| 순서 | 중간에 실패하면 |
| --- | --- |
| 이벤트를 먼저 발행하고 커밋한다 | 커밋이 실패하면 **일어나지 않은 탈퇴가 퍼진다** |
| 커밋한 뒤 이벤트를 발행한다 | 발행 직전에 서버가 죽으면 **탈퇴는 됐는데 아무도 모른다** |

앞에서 쓴 `AFTER_COMMIT` 리스너도 두 번째에 해당합니다. 커밋 직후 애플리케이션이 종료되면 리스너는 실행되지 않고, 그 이벤트는 흔적 없이 사라집니다.

### 3.2 Transactional Outbox Pattern

대표적인 해결 방법이 **Transactional Outbox Pattern**입니다. 이벤트를 곧바로 내보내지 않고, 먼저 **같은 데이터베이스의 테이블(Outbox)에 저장**합니다.

```text
① 하나의 로컬 트랜잭션
   ├─ members 테이블 : 탈퇴 처리
   └─ outbox 테이블  : MemberWithdrawn 이벤트 저장

② 별도의 전달 프로세스
   └─ outbox 테이블에서 아직 보내지 않은 이벤트를 읽어 메시지 브로커에 발행
      └─ 발행에 성공하면 "보냄"으로 표시
```

```sql
CREATE TABLE outbox (
    id           UUID PRIMARY KEY,
    event_type   VARCHAR(100) NOT NULL,
    payload      TEXT         NOT NULL,
    created_at   TIMESTAMP    NOT NULL,
    published_at TIMESTAMP
);
```

탈퇴 처리와 이벤트 저장이 같은 데이터베이스의 같은 트랜잭션이므로, 둘 다 저장되거나 둘 다 취소됩니다. "탈퇴는 됐는데 이벤트는 없다"는 상태가 만들어지지 않습니다. 발행에 실패해도 이벤트는 테이블에 남아 있으므로 다시 시도할 수 있습니다.

대신 알아 둘 점이 있습니다. 전달 프로세스가 브로커에 발행한 직후, "보냄"으로 표시하기 전에 죽으면 같은 이벤트를 다시 보내게 됩니다. Outbox는 **적어도 한 번** 전달을 보장할 뿐, 정확히 한 번을 보장하지 않습니다. 그래서 받는 쪽은 같은 이벤트를 두 번 받아도 결과가 달라지지 않도록(멱등하게) 만들어야 합니다.

### 3.3 Spring Modulith의 Event Publication Registry

Spring 생태계에서는 Spring Modulith의 **Event Publication Registry**가 비슷한 문제를 다룹니다.

- 이벤트를 발행할 때, 어느 리스너에게 전달해야 하는지를 원래 트랜잭션과 함께 데이터베이스에 기록합니다.
- 리스너가 처리를 끝내면 그 기록을 완료로 표시합니다.
- 리스너가 실패했거나 서버가 중간에 죽었다면 기록이 미완료로 남으므로, 나중에 찾아서 다시 처리할 수 있습니다.
- 이벤트를 Kafka 같은 외부 브로커로 내보내는 연계 기능도 제공합니다.

모놀리스 안에서 이벤트로 모듈을 연결하는 단계에서, 직접 Outbox 테이블과 전달 프로세스를 만들지 않고도 이벤트 유실을 추적할 수 있게 해 줍니다.

다만 모든 전달 방식이 Outbox와 완전히 같은 보장을 해 주는 것은 아닙니다. 어떤 방식으로 외부에 내보내느냐에 따라 보장 범위가 달라지므로, 실제로 쓰려는 전달 방식이 무엇을 보장하는지는 공식 문서로 확인해야 합니다.

## 4. 단계적으로 도입하기

| 단계 | 구성 | 얻는 것 | 남는 위험 |
| --- | --- | --- | --- |
| 1 | 프로세스 내 이벤트 (`ApplicationEventPublisher`) | 모듈 간 의존성이 낮아진다 | 서버가 죽으면 이벤트가 유실될 수 있다 |
| 2 | 발행 기록 저장 (Event Publication Registry, Outbox) | 유실된 이벤트를 찾아 다시 처리할 수 있다 | 중복 전달. 받는 쪽이 멱등해야 한다 |
| 3 | 메시지 브로커 (Kafka 등) | 서비스가 분리되어도 이벤트가 전달된다 | 브로커 운영 부담, 순서와 지연 문제 |

지금 당장 Kafka를 도입할 필요는 없습니다. 첫 단계만으로도 "누가 누구를 호출하는가"가 "누가 무슨 사실을 알리는가"로 바뀌고, 이 구조가 갖춰져 있으면 다음 단계로 넘어갈 때 이벤트를 발행하고 받는 코드는 대부분 그대로 둘 수 있습니다.

모든 통신을 이벤트로 바꿔야 하는 것도 아닙니다. 주문하는 순간 회원 상태를 확인해야 하는 경우처럼 즉시 답이 필요한 일에는 동기 호출이 맞습니다. 어떤 요구사항에 어떤 통신 방식이 어울리는지는 [모놀리스에서 MSA로: 구현체 교체로 끝나지 않는 이유](/blog/groups/server/spring_boot/spring_boot_monolith_to_msa)에서 다뤘습니다.

## 5. 마무리

이벤트 기반 설계의 출발점은 메시지 브로커가 아니라, **모듈이 서로를 호출하는 대신 일어난 사실을 알리는 구조**입니다.

- 직접 호출을 이벤트로 바꾸면 알리는 쪽은 듣는 쪽을 몰라도 된다
- BC 내부용인 Domain Event와 외부 공개용 계약인 Integration Event를 구분한다
- 데이터베이스 커밋과 이벤트 발행은 한 트랜잭션이 아니므로, Transactional Outbox Pattern처럼 이벤트를 먼저 데이터베이스에 남기는 방법으로 유실을 막는다
- 이벤트는 중복 전달될 수 있으므로 받는 쪽은 멱등하게 만든다
