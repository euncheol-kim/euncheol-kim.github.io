Kotlin과 DDD 아키텍처 도입을 고민하며 **데이터 가변성 통제(Data Immutability Control)** 의 중요성을 깨닫게 되었습니다.

데이터의 가변성을 통제하면 예기치 못한 데이터 변경으로부터 객체의 상태를 보호하고, 무분별한 상태 변경을 방지할 수 있습니다.

## 데이터 가변성 통제란?

데이터 가변성 통제란 **데이터의 변경 권한과 경계를 명확하게 정의하여, 의도하지 않은 상태 변경을 방지하는 것**을 의미합니다.

예를 들어, 프로젝트에서 다음과 같은 규칙을 정의했다고 가정하겠습니다.

> 도메인이 갖는 데이터의 상태는 도메인이 정의한 행위를 통해서만 변경할 수 있다.

이는 도메인 객체의 상태 변경을 도메인 내부에서 통제하겠다는 의미입니다. 외부의 Service Layer나 다른 객체는 도메인의 내부 상태를 직접 변경할 수 없어야 합니다.

그러나 Java, Kotlin, Python과 같이 객체 참조를 사용하는 프로그래밍 언어에서는 주의해야 할 부분이 있습니다.

**객체를 참조하는 값을 외부에 노출하면, 외부에서도 동일한 객체에 접근할 수 있다는 점입니다.**

예를 들어, 다음 Kotlin 코드를 살펴보겠습니다.

```kotlin
class Order(
    private val items: MutableList<String>,
) {
    fun getItems(): MutableList<String> = items
}

val order = Order(mutableListOf("상품 A"))
order.getItems().clear()
```

`items`를 `private`으로 선언했음에도 외부에서 `clear()`를 호출하여 주문 상품 목록을 변경할 수 있습니다.

Getter가 내부 컬렉션의 참조를 그대로 반환하기 때문입니다.

결국 **접근을 제한하는 것과 객체의 가변성을 통제하는 것은 서로 다른 문제**입니다.

## 객체 참조 공유의 문제

객체 참조가 공유되면 여러 코드에서 동일한 객체의 상태를 변경할 수 있습니다.

이는 데이터의 변경 주체를 불명확하게 만들고, 의도하지 않은 부작용(Side Effect)을 발생시킬 수 있습니다.

특히 DDD에서는 도메인 객체가 항상 만족해야 하는 비즈니스 규칙인 **도메인 불변식(Domain Invariant)** 을 보호하는 것이 중요합니다.

외부에서 도메인의 내부 상태를 직접 변경할 수 있다면, 도메인이 정의한 검증 과정과 비즈니스 규칙을 우회할 가능성이 있습니다.

따라서 데이터의 가변성을 통제하지 않으면 캡슐화가 약화되고, 도메인 상태의 일관성과 예측 가능성을 보장하기 어려워집니다.

## 데이터 가변성을 통제하는 방법

데이터의 가변성을 통제하기 위해서는 다음 세 가지 개념을 이해해야 합니다.

### 1. 캡슐화(Encapsulation)

객체의 내부 상태를 외부에서 직접 변경하지 못하도록 제한하고, 명시적으로 정의된 행위를 통해서만 상태를 변경하도록 설계하는 것입니다.

이를 통해 객체는 자신의 상태와 비즈니스 규칙을 스스로 관리할 수 있습니다.

### 2. 불변성(Immutability)

객체 생성 이후 해당 객체의 상태가 변경되지 않도록 설계하는 것입니다.

불변 객체는 참조가 공유되더라도 기존 상태가 변경되지 않으므로, 예기치 못한 부작용을 줄일 수 있습니다.

단, Kotlin의 `val`이나 읽기 전용 `List`를 사용한다고 해서 참조 대상 객체까지 반드시 불변이 되는 것은 아닙니다.

### 3. 방어적 복사(Defensive Copy)

외부와 데이터를 주고받을 때 기존 가변 객체의 참조를 그대로 공유하지 않고, 필요한 데이터를 복사하여 독립적으로 관리하는 기법입니다.

방어적 복사는 두 가지 방향에서 고려할 수 있습니다.

- **입력 시점:** 외부에서 전달받은 객체가 변경되더라도 내부 상태에 영향을 주지 않도록 보호합니다.
- **출력 시점:** 외부에서 반환받은 객체를 변경하더라도 내부 상태에 영향을 주지 않도록 보호합니다.

다음은 Kotlin에서 방어적 복사와 캡슐화를 적용한 예시입니다.

```kotlin
data class OrderItem(
    val productId: Long,
    val quantity: Int,
)

class Order(initialItems: List<OrderItem>) {
    private val items = initialItems.toMutableList()

    fun getItems(): List<OrderItem> = items.toList()

    fun addItem(item: OrderItem) {
        require(item.quantity > 0)
        items.add(item)
    }
}
```

여기서는 다음과 같이 데이터의 가변성을 통제합니다.

- `toMutableList()`: 외부에서 전달받은 컬렉션과 내부 컬렉션을 분리합니다.
- `toList()`: 내부 컬렉션을 외부에 그대로 노출하지 않고 읽기 전용 형태의 결과를 반환합니다.
- `addItem()`: 도메인이 정의한 행위를 통해서만 상품을 추가하도록 제한합니다.

단, Kotlin의 `toList()`와 `toMutableList()`는 얕은 복사(Shallow Copy)이므로, 컬렉션에 포함된 요소 객체까지 복사하는 것은 아닙니다.

위 예제에서는 `OrderItem`의 프로퍼티가 모두 불변 값이므로, 요소의 참조가 공유되더라도 기존 요소의 상태가 변경되지 않습니다.

## 마무리

데이터 가변성 통제의 핵심은 **모든 데이터를 불변으로 만드는 것이 아니라, 데이터의 변경 권한과 책임을 명확하게 정의하는 것**입니다.

객체 참조가 공유되는 환경에서는 단순히 접근 제어자를 제한하는 것만으로 내부 상태를 완전히 보호할 수 없습니다.

따라서 객체의 책임에 따라 캡슐화, 불변 객체, 방어적 복사를 적절하게 적용해야 합니다.

특히 DDD에서는 도메인의 상태 변경을 명시적인 행위로 제한함으로써 도메인 불변식을 보호하고, 비즈니스 규칙의 일관성을 유지하는 것이 중요합니다.

**데이터의 변경을 허용하되, 변경이 발생하는 경계를 통제하는 것. 이것이 데이터 가변성 통제의 핵심이라고 생각합니다.**
