### 🌱 포스팅 작성 이유

"가능하면 불변으로 만들어라"는 조언은 자주 듣지만, 이유를 물으면 "안전하니까" 정도로 끝나는 경우가 많습니다. 무엇으로부터 안전한지를 특정 언어에 기대지 않고 개념 수준에서 정리합니다.

이 글의 코드는 특정 언어의 문법이 아니라 설명을 위한 의사 코드입니다.

---

## 1. 불변 객체란

**불변 객체(Immutable Object)** 는 생성된 뒤에는 상태가 바뀌지 않는 객체입니다. 반대로 생성 뒤에도 상태를 바꿀 수 있는 객체를 **가변 객체(Mutable Object)** 라고 합니다.

불변 객체의 값을 "바꾸고" 싶을 때는 기존 객체를 고치지 않고 **새 객체를 만듭니다.**

```text
price      = Money(1000)
discounted = Money(price.amount - 200)    // price는 그대로이고, 새 객체가 생긴다
```

---

## 2. 문제의 뿌리: 공유된 가변 상태

불변 객체의 이점은 모두 한 가지 문제에서 출발합니다.

```text
price      = Money(1000)
discounted = price            // 복사가 아니다. 같은 객체를 가리키는 두 번째 이름이다

discounted.amount = 800

print(price.amount)           // 800
```

`price`를 건드린 코드는 한 줄도 없는데 `price`의 값이 바뀌었습니다. 하나의 객체를 여러 곳에서 가리키고 있을 때, 한쪽의 변경이 다른 쪽에 예고 없이 전파됩니다. 이것을 **공유된 가변 상태(Shared Mutable State)** 라고 합니다.

문제가 생기려면 조건 두 가지가 모두 필요합니다.

| 공유 | 가변 | 결과 |
| --- | --- | --- |
| 한다 | 한다 | 한쪽의 변경이 다른 쪽에 전파된다 |
| 한다 | 안 한다 | 안전하다. 누가 봐도 같은 값이다 |
| 안 한다 | 한다 | 안전하다. 바꾸는 쪽이 곧 쓰는 쪽이다 |

객체를 인자로 넘기고, 컬렉션에 담고, 필드에 보관하는 모든 행위가 공유이므로 공유를 없애기는 어렵습니다. 그래서 **가변 쪽을 없애는 것**이 불변 객체의 접근입니다. 3장의 다섯 가지 이점은 모두 이 선택의 결과입니다.

---

## 3. 불변 객체를 지향해야 하는 이유

### 3.1 스레드 안전성(Thread-Safety) 보장

여러 스레드가 같은 데이터를 다룰 때 실행 순서에 따라 결과가 달라지는 문제를 **경쟁 조건(Race Condition)** 이라고 합니다. 경쟁 조건은 다음 세 가지가 **모두** 성립할 때만 발생합니다.

| 조건 | 의미 |
| --- | --- |
| 공유 | 여러 스레드가 같은 객체에 접근한다 |
| 가변 | 그 객체의 상태가 바뀔 수 있다 |
| 동시 | 접근이 같은 시간대에 일어난다 |

- **동시성 문제 해결**: 불변 객체는 두 번째 조건을 없앱니다. 바뀌지 않는 값은 아무리 많은 스레드가 동시에 읽어도 같은 값이므로, 데이터가 꼬이는 일이 생기지 않습니다.
- **동기화 비용 감소**: 락(Lock)이 필요 없어집니다. 이유는 아래에서 풀어 씁니다.

#### 락은 "쓰기"로부터 보호하는 장치다

여기서 말하는 락은 한 번에 한 스레드만 들어오게 하는 **배타적 락**(뮤텍스)입니다. 락이 막으려는 상황은 두 가지입니다.

| 상황 | 문제 |
| --- | --- |
| 쓰기와 쓰기가 겹친다 | 한쪽의 변경이 덮어써져 사라진다 |
| 쓰기와 읽기가 겹친다 | 읽는 쪽이 반쯤 바뀐 값을 본다 |

두 경우 모두 **쓰기**가 끼어 있습니다. 읽기와 읽기만 겹치는 경우는 표에 없습니다. 아무도 값을 바꾸지 않으면, 몇 개의 스레드가 어떤 순서로 읽든 모두 같은 값을 보기 때문입니다.

불변 객체에는 쓰기가 없습니다. 일어날 수 있는 접근은 읽기뿐이고, 읽기끼리는 서로 방해하지 않으므로 보호할 것이 없습니다. 그래서 락을 걸 이유가 없고, 락에 따라오는 대기 시간, 교착 상태, 락을 빠뜨리는 실수도 함께 사라집니다.

단, 락이 필요 없는 것은 **불변 객체 자체**입니다. 여러 스레드가 함께 보는 변수가 "지금 어느 객체를 가리키는가"는 여전히 바뀔 수 있고, 이 교체는 동기화가 필요합니다.

```text
shared = Money(1000)              // 여러 스레드가 함께 보는 변수

shared = Money(shared.amount + 100)    // 읽고 → 새로 만들고 → 교체한다
// 두 스레드가 동시에 실행하면 한쪽의 교체가 사라질 수 있다
```

불변 객체는 동기화가 필요한 범위를 "객체 내부의 모든 값"에서 **"참조 하나를 교체하는 순간"** 으로 줄여 줍니다. 문제를 없애는 것이 아니라 한 점으로 모으는 것입니다.

### 3.2 사이드 이펙트(부작용) 방지와 디버깅 용이성

함수가 결과를 돌려주는 것 외에 바깥의 상태를 바꾸는 것을 **사이드 이펙트(Side Effect)** 라고 합니다.

- **상태 추적 불필요**: 가변 객체의 값이 이상할 때는 "언제, 어디서, 누가 바꿨는가"를 거슬러 올라가야 합니다. 불변 객체는 생성된 시점의 상태가 끝까지 유지되므로, 값이 이상하다면 원인은 **만들어진 곳 한 군데**에 있습니다.
- **안전한 데이터 전달**: 객체를 다른 함수나 외부 모듈에 넘길 때, 그쪽에서 내 데이터를 바꿀까 걱정할 필요가 없습니다. 넘기기 전에 복사본을 만들어 두는 [방어적 복사](/blog/programming_concept/defensive_copy)도 필요 없어집니다.

```text
order = createOrder()
validate(order)
notify(order)
save(order)        // 무엇이 저장되는가?
```

`order`가 가변이라면 `validate`와 `notify`의 내부까지 읽어야 답할 수 있습니다. 불변이라면 읽지 않아도 됩니다. `createOrder()`가 돌려준 그대로입니다.

### 3.3 실패 원자성(Failure Atomicity) 제공

작업이 실패했을 때 객체가 **작업 이전의 상태 그대로** 남는 성질을 **실패 원자성**이라고 합니다. "전부 반영되거나, 전혀 반영되지 않거나" 둘 중 하나만 일어난다는 뜻입니다.

가변 객체는 여러 값을 차례로 고치는 도중에 예외가 나면 **반쯤 바뀐 상태**로 남습니다.

```text
// 가변: 기존 객체를 직접 고친다
function applyDiscount(order):
    order.price  = order.price - 1000
    order.coupon = findCoupon()        // 여기서 예외 발생
    order.status = "DISCOUNTED"

// 결과: 가격만 깎이고 쿠폰과 상태는 그대로인 order가 남는다
```

불변 객체는 기존 객체를 고치지 않고 새 객체를 만들기 때문에, 만드는 도중에 실패하면 새 객체가 생기지 않을 뿐입니다.

```text
// 불변: 새 객체를 만든다
function applyDiscount(order):
    coupon = findCoupon()              // 여기서 예외 발생
    return Order(order.price - 1000, coupon, "DISCOUNTED")

// 결과: 새 객체는 만들어지지 않았고, 기존 order는 온전하다
```

- **일관된 상태 유지**: 예외가 발생해도 기존 객체는 오염되지 않습니다. 실패한 뒤에도 기존 객체를 그대로 믿고 쓸 수 있으므로, 복구 코드를 따로 작성할 필요가 없습니다.

객체가 항상 만족해야 하는 조건인 **불변식(Invariant)** 도 같은 원리로 지켜집니다. 불변 객체는 생성 시점에 한 번 검증하면 그 뒤로는 깨질 수 없습니다. 가변 객체는 값을 바꾸는 모든 경로에서 검증을 반복해야 합니다.

### 3.4 컬렉션과 캐싱(Caching)에서의 안정성

- **안전한 키(Key) 사용**: 해시 기반의 맵(Map)과 집합(Set)은 객체를 넣는 순간의 해시값으로 보관 위치를 정합니다. 키로 넣은 가변 객체의 내부 값을 나중에 바꾸면 해시값이 달라지고, 컬렉션은 그 객체를 엉뚱한 위치에서 찾게 됩니다. 데이터는 안에 있는데 꺼낼 수 없는 상태가 됩니다. 불변 객체는 해시값이 변하지 않으므로 이런 일이 일어날 수 없습니다.
- **자유로운 재사용**: 값이 바뀌지 않으므로 같은 값의 객체를 매번 새로 만들 필요가 없습니다. 하나를 만들어 캐싱해 두고 여러 곳에서 함께 써도 안전합니다. 가변 객체를 이렇게 공유하면 한 곳의 변경이 캐시를 쓰는 모든 곳에 퍼집니다.

### 3.5 가독성과 유지보수성 향상

- **코드 이해 속도 증가**: 가변 객체가 있는 코드를 읽을 때는 "이 시점에 이 변수의 값이 무엇인가"를 머릿속으로 계속 따라가야 합니다. 불변이면 처음 정해진 값이 끝까지 가므로 그럴 필요가 없습니다.

코드의 한 부분만 읽고 동작을 확신할 수 있는 성질을 **지역적 추론(Local Reasoning)** 이라고 합니다. 가변 객체에서는 이해해야 할 범위가 "그 객체에 닿을 수 있는 모든 코드"로 넓어지고, 불변 객체에서는 "객체가 만들어진 곳"으로 좁혀집니다.

### 3.6 정리

| 이점 | 불변이 없애 주는 것 |
| --- | --- |
| 스레드 안전성 | 경쟁 조건, 락 |
| 사이드 이펙트 방지 | 값이 바뀐 지점 추적, 방어적 복사 |
| 실패 원자성 | 반쯤 바뀐 상태, 복구 코드 |
| 컬렉션과 캐싱의 안정성 | 해시값 변동, 캐시 오염 |
| 가독성과 유지보수성 | 머릿속 상태 시뮬레이션 |

## 4. 더 알아 두면 좋은 것

### 4.1 재할당 금지와 불변은 다르다

많은 언어에 "한 번 정하면 다시 대입할 수 없다"는 키워드가 있습니다.

| 언어 | 키워드 |
| --- | --- |
| Java | `final` |
| Kotlin | `val` |
| JavaScript | `const` |

이 키워드들이 막는 것은 **변수가 다른 객체를 가리키게 바꾸는 것**뿐입니다. 변수가 가리키는 객체의 내부까지 고정하지는 않습니다.

```text
const cart = Cart(items: ["사과"])

cart = otherCart            // ❌ 재할당은 막힌다
cart.items.add("배")        // ✅ 내부는 여전히 바뀐다
```

| 구분 | 의미 |
| --- | --- |
| 얕은 불변(Shallow Immutability) | 객체가 직접 가진 값만 고정된다. 그 값이 가리키는 다른 객체는 바뀔 수 있다 |
| 깊은 불변(Deep Immutability) | 객체가 가진 것, 그것이 가진 것까지 전부 고정된다 |

3장의 이점은 깊은 불변일 때만 온전히 성립합니다.

### 4.2 불변의 비용과 구조적 공유

불변이 공짜는 아닙니다. 값이 바뀔 때마다 새 객체를 만들어야 하므로, 원소 백만 개짜리 컬렉션에서 하나만 바꾸려 해도 원칙적으로는 새 컬렉션이 필요합니다.

이 비용을 줄이는 기법이 **구조적 공유(Structural Sharing)** 입니다. 새 객체를 만들 때 전체를 복사하지 않고, **바뀌지 않은 부분은 기존 객체의 것을 그대로 가리키게** 합니다.

```text
before = [A, B, C, D]
after  = before에서 D를 E로 바꾼 것

// after는 A, B, C를 새로 만들지 않고 before의 것을 함께 쓴다
// 새로 만들어지는 것은 E와, E로 가는 경로뿐이다
```

공유된 부분도 불변이므로 누구도 바꿀 수 없고, 그래서 함께 써도 안전합니다. **불변이기 때문에 공유가 가능한** 것입니다. 이 방식으로 만든 자료구조를 영속 자료구조(Persistent Data Structure)라고 합니다.

### 4.3 무엇을 불변으로 만드는가: 값 객체와 엔티티

모든 객체를 불변으로 만들 수는 없습니다. 기준이 되는 구분이 있습니다.

| 구분 | 무엇으로 구별하는가 | 예시 | 불변 여부 |
| --- | --- | --- | --- |
| 값 객체(Value Object) | 가진 값 | 금액, 기간, 좌표, 주소 | 불변으로 만든다 |
| 엔티티(Entity) | 정체성(식별자) | 회원, 주문, 계좌 | 상태가 변하는 것이 본질이다 |

1000원짜리 금액 두 개는 구별할 필요가 없습니다. 값이 같으면 같은 것입니다. 이런 객체는 "값을 바꾼다"는 것이 곧 "다른 값이 된다"는 뜻이므로 불변으로 만드는 것이 자연스럽습니다.

회원은 이름을 바꿔도 같은 회원입니다. 시간이 흐르며 상태가 변하는 것이 본질이므로 완전히 불변으로 만들 수 없습니다. 대신 **상태를 바꾸는 방법을 그 객체가 정한 메서드로만 제한**하고, 엔티티가 가진 값들은 값 객체로 구성합니다.

### 4.4 "지향한다"는 말의 의미

프로그램은 결국 무언가를 바꾸기 위해 존재합니다. 불변을 지향한다는 것은 가변을 금지한다는 뜻이 아니라 다음 두 가지를 뜻합니다.

1. **기본값을 불변으로 둔다.** "가변으로 만들었다가 필요하면 막는다"가 아니라 "불변으로 만들었다가 필요하면 연다"의 순서입니다.
2. **가변 상태를 좁은 곳에 모은다.** 변경이 꼭 필요한 상태는 소수의 객체 안에 가두고, 나머지 대부분은 불변인 값으로 둡니다.

가변성을 없애는 것이 아니라, **가변성이 있는 위치를 알 수 있게 만드는 것**이 목표입니다.

## 5. 마무리

한 곳의 변경이 서로 모르는 다른 곳에 영향을 주는 공유된 가변 상태가 문제의 뿌리이고, 불변 객체는 그중 "가변"을 제거합니다.

그 결과로 여러 스레드가 함께 써도 안전하고, 값이 몰래 바뀌지 않으며, 실패해도 기존 상태가 온전하고, 컬렉션의 키와 캐시로 믿고 쓸 수 있고, 코드를 읽기 쉬워집니다.

**불변 객체는 "언제 봐도 같은 값"을 보장하는 대신 "바꿀 때마다 새로 만든다"는 비용을 치릅니다.** 대부분의 코드에서는 이 교환이 이득이므로, 기본을 불변으로 두고 가변은 꼭 필요한 곳에만 좁게 허용합니다.
