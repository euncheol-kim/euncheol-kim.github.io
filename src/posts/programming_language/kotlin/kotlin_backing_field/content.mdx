### 🌱 포스팅 작성 이유

Kotlin을 학습하던 중 아래 문장을 읽고 의미가 한 번에 와닿지 않았습니다.

> field를 사용하지 않는 커스텀 접근자 구현을 정의한다면, 컴파일러는 프로퍼티가 아무 정보도 저장하지 않는 것으로 이해하고, 뒷받침하는 필드를 생성하지 않는다.

이 문장을 이해하려면 Kotlin에서 **프로퍼티(Property)** 와 **필드(Field)** 가 서로 다른 개념이라는 점을 먼저 알아야 합니다. Java의 관점에서 Kotlin 프로퍼티가 어떻게 컴파일되는지 따라가며 정리합니다.

> 접근자, 기본 접근자, 초기화 식 같은 용어가 낯설다면 [Kotlin 프로퍼티 기초](/blog/kotlin/kotlin_property_basics)를 먼저 읽는 것을 권합니다.

---

## 1. 프로퍼티와 필드는 다르다

Java에서는 값을 저장하는 **필드**와 그 값을 읽고 쓰는 **getter/setter**를 개발자가 직접 작성합니다.

```java
public class Person {
    private int birthYear;                          // 필드 (값 저장)

    public int getBirthYear() { return birthYear; } // getter
    public void setBirthYear(int v) { birthYear = v; } // setter
}
```

Kotlin에서는 이 세 가지를 **프로퍼티** 하나로 묶어서 선언합니다.

```kotlin
class Person(var birthYear: Int)
```

컴파일러는 위 한 줄을 보고 Java 코드와 동일한 구조를 만들어 냅니다. 값을 저장할 `birthYear` 필드, 그것을 읽는 `getBirthYear()`, 그것에 쓰는 `setBirthYear(int)`입니다.

즉, Kotlin의 프로퍼티는 **접근자(getter/setter)의 묶음**이고, 필드는 그 접근자가 값을 넣어 두는 **저장 공간**입니다. 프로퍼티를 선언했다고 해서 항상 저장 공간이 생기는 것은 아닙니다. 저장 공간이 필요한 경우에만 컴파일러가 만들어 주며, 이렇게 프로퍼티를 뒤에서 받쳐 주는 저장 공간을 **뒷받침하는 필드(Backing Field)** 라고 부릅니다.

---

## 2. 기본 접근자는 항상 Backing Field를 사용한다

접근자를 직접 작성하지 않으면 컴파일러가 **기본 접근자**를 만들어 줍니다. 기본 getter는 저장된 값을 그대로 돌려주고, 기본 setter는 받은 값을 그대로 저장합니다.

```kotlin
class Person(var birthYear: Int)
// 기본 getter : get() = field
// 기본 setter : set(value) { field = value }
```

둘 다 값을 저장할 공간이 있어야 동작하므로, 기본 접근자를 하나라도 사용하는 프로퍼티에는 Backing Field가 항상 생성됩니다.

---

## 3. 커스텀 접근자와 field 식별자

접근자를 직접 정의할 때는 `get()`과 `set(value)` 블록을 사용하고, 그 안에서 `field`라는 식별자로 **자기 프로퍼티의 Backing Field**에 접근합니다.

```kotlin
class Person(birthYear: Int) {
    var birthYear: Int = birthYear
        set(value) {
            require(value > 0) { "출생 연도는 양수여야 합니다." }
            field = value        // Backing Field에 저장
        }
}
```

위 setter는 검증 로직을 추가했을 뿐, 최종적으로는 `field`에 값을 저장합니다. **`field`를 사용했다는 것은 "이 프로퍼티는 값을 저장해야 한다"고 컴파일러에게 알리는 것**과 같습니다. 그래서 컴파일러는 Backing Field를 생성합니다.

참고로 `field` 대신 프로퍼티 이름을 쓰면 접근자가 자기 자신을 다시 호출하여 `StackOverflowError`가 발생합니다.

```kotlin
var birthYear: Int = 0
    get() = birthYear      // ❌ getBirthYear() 안에서 getBirthYear() 호출
```

## 4. field를 사용하지 않는 커스텀 접근자

이제 처음의 문장으로 돌아가겠습니다.

```kotlin
class Person(var birthYear: Int) {
    var ageIn2050: Int
        get() = 2050 - birthYear
        set(value) {
            birthYear = 2050 - value
        }
}
```

`ageIn2050`의 getter와 setter를 살펴보면 **어디에도 `field`가 등장하지 않습니다.**

- getter는 `birthYear`로부터 값을 **계산**해서 돌려줍니다.
- setter는 받은 값을 `ageIn2050`에 저장하는 대신 **`birthYear`를 바꿉니다.**

`ageIn2050`은 자신만의 값을 어디에도 저장하지 않습니다. 모든 정보는 `birthYear`에 있고, `ageIn2050`은 그 값을 다른 형태로 보여 주는 **창구** 역할만 합니다.

컴파일러는 이를 보고 다음과 같이 판단합니다.

> getter도 setter도 `field`를 쓰지 않으니, 이 프로퍼티는 저장할 값이 없다. Backing Field를 만들 필요가 없다.

이것이 "프로퍼티가 아무 정보도 저장하지 않는 것으로 이해하고, 뒷받침하는 필드를 생성하지 않는다"는 문장의 의미입니다.

### 4.1 Java 관점에서 확인하기

위 클래스를 컴파일한 뒤 디컴파일하면 다음과 비슷한 구조가 됩니다.

```java
public final class Person {
    private int birthYear;                       // birthYear의 Backing Field

    public final int getBirthYear() { return birthYear; }
    public final void setBirthYear(int v) { birthYear = v; }

    // ageIn2050 필드는 존재하지 않는다
    public final int getAgeIn2050() { return 2050 - birthYear; }
    public final void setAgeIn2050(int value) { birthYear = 2050 - value; }
}
```

`birthYear` 필드는 있지만 `ageIn2050` 필드는 없습니다. `ageIn2050`은 **메서드 두 개로만 존재하는 프로퍼티**입니다.

```kotlin
val person = Person(birthYear = 1995)
println(person.ageIn2050)   // 55   getAgeIn2050() 호출 → 2050 - 1995 계산

person.ageIn2050 = 30       //      setAgeIn2050(30) 호출 → birthYear = 2020
println(person.birthYear)   // 2020
println(person.ageIn2050)   // 30   2050 - 2020 을 다시 계산
```

## 5. Backing Field가 생성되는 조건

컴파일러는 다음 중 하나라도 해당할 때 Backing Field를 생성합니다.

1. getter 또는 setter 중 하나라도 **기본 접근자**를 사용한다.
2. 커스텀 접근자 안에서 **`field`를 참조**한다.

반대로, 모든 접근자를 직접 정의했고 그 안에서 `field`를 한 번도 쓰지 않았다면 Backing Field는 생성되지 않습니다.

| 선언 | Backing Field | 이유 |
| --- | --- | --- |
| `var a: Int = 0` | 생성 | 기본 getter/setter가 field를 사용 |
| `var a: Int = 0` + `set(v) { field = v * 2 }` | 생성 | getter는 기본, setter는 field 사용 |
| `val a: Int get() = b + 1` | 생성 안 함 | field 미사용, 저장할 값 없음 |
| `var a: Int get() = b set(v) { b = v }` | 생성 안 함 | field 미사용, 저장할 값 없음 |

Backing Field는 클래스 단위가 아니라 **프로퍼티 하나하나마다** 있거나 없거나가 결정됩니다. 4장의 `Person`에서 `birthYear`에는 있고 `ageIn2050`에는 없는 것처럼, 같은 클래스 안에서도 프로퍼티마다 다릅니다.

---

## 6. Backing Field가 없을 때 달라지는 점

Backing Field가 없다는 것은 곧 "저장 공간이 없다"는 뜻입니다. 여기서 세 가지가 따라 나옵니다.

### 6.1 초기화 식을 쓸 수 없다

초기화 식 `= 값`은 "객체 생성 시 이 값을 Backing Field에 넣어라"는 명령입니다. 넣을 공간이 없으면 컴파일 에러가 납니다.

```kotlin
var ageIn2050: Int = 0              // ❌ Initializer is not allowed here
    get() = 2050 - birthYear        //    because this property has no backing field
    set(value) { birthYear = 2050 - value }
```

`= 0`을 적는다고 Backing Field가 생기지는 않습니다. 생성 여부는 오직 접근자가 `field`를 쓰느냐로만 결정되기 때문에, `= 0`이 있어도 공간은 생기지 않고 결국 `= 0`이 에러가 됩니다.

같은 이유로 `val`은 평소에 초기화 없이 선언하면 에러가 나지만, `field`를 쓰지 않는 getter를 붙이면 초기화 없이 선언할 수 있습니다. 저장할 값이 없으니 초기화할 필요도 없기 때문입니다.

```kotlin
val isAdult: Boolean          // ✅ 초기화 식 없음, 그래도 에러 아님
    get() = age >= 19
```

### 6.2 메모리를 차지하지 않는다

`Person` 객체에는 `birthYear`를 위한 `int` 하나만 있습니다. `ageIn2050`은 객체가 가진 데이터가 아니라 데이터를 바라보는 하나의 시각일 뿐이므로, 인스턴스를 아무리 많이 만들어도 `ageIn2050`을 위한 공간은 추가되지 않습니다.

### 6.3 접근할 때마다 다시 계산된다

저장된 값을 꺼내 오는 것이 아니라 접근할 때마다 getter가 실행됩니다. 그래서 `birthYear`가 바뀌면 `ageIn2050`도 항상 최신 값을 돌려줍니다. 반대로 getter 안의 계산이 무겁다면 접근 횟수만큼 그 비용이 반복되므로, 그런 경우에는 `by lazy` 등으로 결과를 저장해 두는 쪽이 적절합니다.

---

## 7. 마무리

Kotlin의 프로퍼티는 **값을 저장하는 공간**이 아니라 **값에 접근하는 방법(getter/setter)** 을 선언하는 것입니다. 저장 공간인 Backing Field는 접근자가 `field`를 필요로 할 때만 컴파일러가 만들어 줍니다.

`ageIn2050`처럼 모든 접근자가 다른 프로퍼티에 의존하고 `field`를 전혀 쓰지 않는다면, 그 프로퍼티는 저장하는 것이 없는 **계산 프로퍼티**가 되며 컴파일러는 저장 공간을 만들지 않습니다.

**프로퍼티는 인터페이스이고, 필드는 구현 세부 사항입니다. `field`를 쓰느냐가 그 구현 세부 사항의 존재 여부를 결정합니다.** 이것이 그 문장의 핵심이라고 생각합니다.
